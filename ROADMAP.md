# PhoneCam — план работ

Собственная замена DroidCam: телефон как полноценная веб-камера в Windows.
Приватный проект, один пользователь, без установщика и без подписок.

**Точка входа для того, кто продолжает работу — [`HANDOFF.md`](HANDOFF.md).**
Там карта файлов, что проверено и что нет, оба протокола (разделяемая память и
MJPEG), все решения с обоснованием и конкретный план этапа 3. Этот файл —
журнал планов и грабель, тот — передача состояния.

## Из чего состоит

| Часть | Язык | Что делает |
|---|---|---|
| `vcam/PhoneCamFilter.cpp` | C++ | DirectShow-фильтр. Регистрируется в системе и выглядит для Windows как обычная камера. |
| `server/` | Rust | Принимает поток с телефона, кладёт кадры в разделяемую память. |
| `android/` | Kotlin | Снимает камеру телефона, кодирует и шлёт по Wi-Fi. |
| `vcam/PhoneCamProtocol.h` | — | Контракт разделяемой памяти между сервером и фильтром. |

Почему Rust, а не C#: один `.exe` на несколько мегабайт, без рантайма и без
россыпи DLL. Почему не Python: GIL и задержка на реалтайм-видео.

## Этапы

Каждый этап заканчивается работающей вещью, на которой можно остановиться.

- [x] **0. Каркас.** Протокол, фильтр, сборка, тестовый сигнал.
- [x] **1. Виртуальная камера работает.** `PhoneCam.dll` собран и зарегистрирован,
      `phonecam-server` рисует тестовый сигнал, камера отдаёт кадры.
      Это единственное место, где что-то может принципиально не получиться,
      поэтому оно и шло первым.
- [ ] **2. Android-клиент.** Приложение на Kotlin: камера → MJPEG по HTTP.
      Проверяется без сервера — открыть адрес в браузере ПК.
      Код написан, APK собирается (4.2 МБ, `com.phonecam`, minSdk 24). **На
      телефоне ещё не запускался** — этап не закрыт, пока кадр не увиден
      в браузере.
- [ ] **3. Приём на сервере.** Rust читает тот же MJPEG-поток, декодирует JPEG,
      рисует в разделяемую память вместо тестового сигнала. **Всё вместе
      работает.**
- [ ] **4. H.264 вместо JPEG.** Аппаратный `MediaCodec` на телефоне,
      аппаратный декодер Media Foundation на ПК. Меньше трафика, меньше задержка.
- [ ] **5. Обвязка.** Трей, QR-код для подключения, автозапуск, выбор
      камеры/разрешения/битрейта.

## Что уже решено и почему

**DirectShow, а не Media Foundation Virtual Camera.** `MFCreateVirtualCamera`
требует написать `IMFMediaSource` (намного больше COM-кода) и пересоздавать
камеру после каждой перезагрузки. Фильтр DirectShow регистрируется один раз
через `regsvr32` и живёт сам. Media Foundation умеет мостить DirectShow-устройства,
так что современные приложения видят его в обоих случаях.

**Фильтр самодостаточный, без базовых классов DirectShow.** Они больше не
поставляются с Windows SDK, а тащить их из зеркала — это вендорить пару тысяч
строк чужого кода в проект, который задуман своим.

**Разделяемая память, а не драйвер.** Фильтр только читает, сервер только
пишет. Поэтому сервер можно перезапускать, а фильтр переживёт это и покажет
«нет сигнала».

**TCP, а не WebRTC.** На домашнем Wi-Fi не нужны ICE и NAT-трюки, а аппаратный
H.264-энкодер на Android доступен напрямую через `MediaCodec`. TCP убирает всю
возню с потерями и переупорядочиванием.

**MJPEG по HTTP на этапе 2, а не свой формат кадров.** Браузер показывает
`multipart/x-mixed-replace` в обычном `<img>` без единой строки клиентского
кода. Значит телефон проверяется с ПК ещё до того, как написан сервер, — и
Rust на этапе 3 читает ровно те же байты, которые браузер уже показал
правильными. Отлаживать приходится один транспорт, а не два.

## Грабли, которые уже известны

- **Перевёрнутая картинка.** В `FillVideoInfoHeader` высота отрицательная
  (строки сверху вниз). Проверяется серым квадратом в левом верхнем углу
  тестового сигнала: полосы и кольцо симметричны, поэтому без него кадр
  вверх ногами выглядит точно так же, как правильный. Квадрат не в левом
  верхнем углу = зеркало, переворот или и то и другое.
- **Соотношение сторон.** Кольцо в тестовом сигнале должно быть круглым.
  Овал = ошибка в stride или в масштабировании.
- **Регистрация x64 vs x86.** Сейчас регистрируется только 64-битная версия.
  32-битные приложения камеру не увидят — маловероятно, но возможно.
- **Порядок запуска.** Сервер владеет разделяемой памятью. Если он не запущен,
  фильтр показывает тёмно-серый «нет сигнала» — это норма, а не поломка.

## Как проверить этап 1

```
cd vcam
build.bat            # соберёт PhoneCam.dll
register.bat         # запросит админа и зарегистрирует

cd ..\server
cargo run --release  # запустит тестовый сигнал

# открыть любое приложение, где есть выбор камеры, и выбрать "PhoneCam"
```

Проверить, не открывая Zoom и не глядя глазами, можно через ffmpeg — он видит
фильтр как обычное dshow-устройство:

```
ffmpeg -f dshow -list_devices true -i dummy          # "PhoneCam" в списке
ffmpeg -f dshow -video_size 1280x720 -i video=PhoneCam -frames:v 1 frame.png
```

Что проверять в кадре: цвета полос без подмены R↔B, серый квадрат в левом
верхнем углу (ориентация), кольцо круглое (овал = ошибка stride), белая полоса
едет слева направо примерно 43 px за кадр, а без запущенного сервера кадр —
ровно один цвет `30,20,24`.

## Как проверить этап 2

```
cd android
gradlew.bat assembleDebug
# APK: app\build\outputs\apk\debug\app-debug.apk
```

Скопировать APK на телефон, установить (Android спросит разрешение на установку
из неизвестного источника), открыть, выдать доступ к камере, нажать Start.
На экране появится адрес вида `http://192.168.х.х:8080/` — открыть его в
браузере ПК, который в той же сети Wi-Fi.

Что проверять: картинка с камеры, не перевёрнутая и не боком; в строке статуса
на телефоне счётчик подключений стал 1. Если картинка боком — значит на
телефоне `rotationDegrees` не 0, и это видно в подписи под кадром на странице.

## Наблюдения, которых не было в плане

- **Приложение открыто раньше сервера.** Фильтр не отдавал ни одного кадра,
  пока не открывалась разделяемая память: приложение, запущенное до сервера,
  висело на чёрном экране вместо карточки «нет сигнала». Исправлено — кадр
  отдаётся всегда, а попытка открыть память повторяется раз в секунду.
- **Разрыв кадра был настоящим.** Однобуферная версия давала видимый шов:
  верхние строки кадра из предыдущего кадра, нижние из текущего. Замерено
  примерно раз на 30–60 кадров, шов нашёлся на y=108/109. Сделаны два буфера
  и seqlock-счётчик: продюсер рисует в неактивный буфер, читатель копирует
  только при чётном счётчике и после копии проверяет, что счётчик не ушёл
  на полный цикл. На 500 кадрах в двух колонках — ноль разрывов.
- **Осторожно с выводами по одному замеру.** Убедившись однажды, что разрыва
  нет, я записал это в план — и ошибся: детектор был нечувствителен к тому,
  что разрыв сдвигает только бегущую полосу, а статичные полосы оставляет на
  месте. Прежде чем верить замеру, надо проверить его на заведомо плохом
  кадре.

- **CameraX больше не отдаёт аппаратный JPEG.** В 1.6.2 у `ImageAnalysis`
  остались только `OUTPUT_IMAGE_FORMAT_YUV_420_888`, `RGBA_8888` и `NV21` —
  константу `OUTPUT_IMAGE_FORMAT_JPEG` убрали, и сборка падает на
  «Unresolved reference». Взят `NV21`: его `YuvImage.compressToJpeg` жмёт одним
  нативным вызовом, без цикла по пикселям. Проверять такие вещи надо не по
  памяти, а по самому классу — `javap` по `classes.jar` из скачанного AAR.

- **Поворот кадра отдан ПК, а не телефону.** CameraX умеет отдать JPEG, но не
  умеет его повернуть — ориентация приходит только числом `rotationDegrees`.
  Единственный доступный разворот на телефоне — декод, поворот,
  перекодирование, то есть три прохода по каждому кадру на самом слабом и
  батарейном устройстве в системе. ПК этот кадр всё равно декодирует, поэтому
  поворот стоит там копирования памяти. Телефон сообщает угол заголовком
  `X-PhoneCam-Rotation`, браузер применяет его как CSS, сервер на этапе 3 —
  при декодировании. Байты в сети при этом одинаковые для обоих.

- **Android SDK пришлось ставить с нуля.** Ни SDK, ни adb, ни Gradle в системе
  не было. `sdkmanager` и новый `android sdk list` падают с 0xC0000409, зато
  `android create` и `android sdk install` работают — и `android create`
  попутно сам поставил `platforms/android-36`. Версии AGP и Gradle взяты
  оттуда, а не подобраны: 9.0.1 и 9.1.0.

- **JDK 25 подошёл.** Gradle 9.1.0 заявляет полную поддержку Java 25, так что
  отдельный JDK для сборки не понадобился. JDK 17 для `jvmToolchain` Gradle
  скачивает сам через foojay.
